# T4H Command Layer — Live Signal Feed + Two-Way State Model

## Purpose
Capture the Portal and Explorer pattern: signals flow through the system, staff can request changes, agents can apply safe changes, and every change must update the registry and evidence state.

## Core thesis
Doolittles is two-way and stateful. It is not just executive broadcast. It is an operating mesh where people, systems and agents continuously exchange signals, requests and proof.

## Product lines
- Watch signals become action.
- Staff shape the system. The system learns from staff.
- Every signal has a state. Every change has proof.

---

## Current UI surfaces observed

### Portal — Live Signal Feed
Shows detected, triaged, routed and resolved signals.

Example feed:
- New supply-chain risk detected — routed to Operations Lead.
- PM agent auto-triaged 14 signals, escalated 2 to human review.
- Email alert generated by augmented team — incident auto-resolved before human review.
- Product Lead signal feed updated — 3 new roadmap items queued.

### Explorer — Registry
Shows roles, signals, assets and states.

Existing visible entries include:
- Project Manager — Role — Assisted.
- Data Analyst — Role — Augmented.
- Product Lead — Role — Assisted.
- Strategy Director — Role — As-Is.
- Comms Lead — Role — As-Is.
- Market Shift Q1 — Signal — High.

---

## Required next model
The Portal and Explorer should be connected.

Live Signal Feed should not be visual theatre. Every feed item should map to:
- a registry entity;
- a state transition;
- an owner or role;
- an agent pod;
- a system action;
- proof / evidence.

## Signal lifecycle

```yaml
signal_lifecycle:
  states:
    - detected
    - classified
    - routed
    - actioned
    - validated
    - resolved
    - learned
  failure_states:
    - blocked
    - escalated
    - rejected
    - rollback_required
```

---

## Two-way flow

### Top-down
Executive announcement becomes signals and system actions.

### Bottom-up
Staff request becomes configuration change or new signal rule.

### Sideways
System event in one tool updates another tool.

Example:
ServiceNow ticket created -> Slack notification -> LMS training update -> HoloWall readiness state.

## Data model

### command_events
```sql
create table if not exists command_events (
  id uuid primary key default gen_random_uuid(),
  command_key text not null,
  source text not null,
  raw_text text not null,
  intent text,
  status text default 'received',
  created_at timestamptz default now()
);
```

### signal_events
```sql
create table if not exists signal_events (
  id uuid primary key default gen_random_uuid(),
  command_id uuid,
  signal_key text not null,
  title text not null,
  severity text,
  domain text,
  current_state text default 'detected',
  routed_to text,
  agent_pod text,
  evidence jsonb default '{}'::jsonb,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```

### registry_entities
```sql
create table if not exists registry_entities (
  id text primary key,
  name text not null,
  entity_type text not null,
  stage text,
  description text,
  owner_role text,
  systems text[],
  agent_pods text[],
  metadata jsonb default '{}'::jsonb,
  updated_at timestamptz default now()
);
```

### system_change_requests
```sql
create table if not exists system_change_requests (
  id uuid primary key default gen_random_uuid(),
  requester text,
  source_channel text,
  raw_request text not null,
  request_type text,
  risk_level text,
  affected_systems text[],
  human_gate_required boolean default false,
  status text default 'received',
  action_taken jsonb default '{}'::jsonb,
  rollback_available boolean default false,
  evidence jsonb default '{}'::jsonb,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```

### tool_activation_events
```sql
create table if not exists tool_activation_events (
  id uuid primary key default gen_random_uuid(),
  command_id uuid,
  signal_id uuid,
  tool_name text not null,
  action text not null,
  status text default 'queued',
  proof jsonb default '{}'::jsonb,
  created_at timestamptz default now(),
  updated_at timestamptz default now()
);
```

## UI upgrade requirements

### Portal feed card
Every signal card should show:
- state;
- routed role;
- agent pod;
- systems touched;
- action taken;
- evidence badge;
- rollback availability where relevant.

### Explorer row
Every registry row should link back to:
- related signals;
- related commands;
- related assets;
- current state;
- maturity: As-Is / Assisted / Augmented / Autonomous.

### Two-way change card
For staff requests, show:
- human request;
- interpreted command object;
- risk classification;
- system changes applied;
- audit log receipt.

### Before
Signals are scattered across email, Slack, tools and meetings. People manually interpret them and update systems later.

### After
Signals enter the Command Layer. They are classified, routed, actioned, validated and reflected in the registry.

The Explorer shows what the organisation knows. The Portal shows what the organisation is doing.
