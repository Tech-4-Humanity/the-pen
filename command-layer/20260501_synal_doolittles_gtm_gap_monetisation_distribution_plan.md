# Synal / Doolittles — GTM Gap, Monetisation, Product, Pricing, Sales, Marketing, Distribution and Repeatability Plan

## Purpose
Assess issues, gaps, monetisation, product/pricing, barriers to go, sales, marketing, distribution and repeatability for the current Synal/Doolittles/Command Layer direction.

## Executive judgement
The direction is strong, but the product must be split into two realities:

1. What can sell now: Doolittles Message-to-Action + Signal Button + Proof-of-Done.
2. What becomes the premium suite later: Synal browser/dock/multi-surface operating layer.

The generated Synal UI visual is strong enough for a pitch and prototype direction. It is not yet proof. The next commercial milestone is a live fake-browser demo with signup and one real Signal -> Output -> Proof loop.

---

## 1. Current issues

### Issue 1 — Scope gravity
Synal is big: browser, widgets, TV, car, mobile, agent dock, proof, tools and surfaces.

Risk: it becomes impressive but not shippable.

Response: lead with Doolittles and Signal Button; keep Synal as upsell/demo surface.

### Issue 2 — Demo vs reality confusion
The fake browser can look complete while no runtime exists.

Risk: false confidence and another paper city.

Response: every screen must label state: Demo, Stub, Live, or Proofed.

### Issue 3 — Too many SKUs
The catalogue is valuable, but 30+ SKUs can bury execution.

Risk: product sprawl.

Response: ship three first offers only:
- Doolittles Message-to-Action Demo
- Signal Button
- Proof-of-Done Widget

### Issue 4 — Integration overreach
Slack, ServiceNow, Salesforce, SAP and Microsoft all matter, but live integration with all of them is too much for first proof.

Risk: time-to-market death.

Response: use stubs for most; make one simple real write path live first: Supabase evidence log and lead capture. Then add Slack webhook.

### Issue 5 — Proof gap
The entire brand promises reality and evidence.

Risk: if proof is fake, the brand collapses.

Response: proof panel must write at least one real row to Supabase or GitHub receipt log.

## 5. Barriers to go

### Barrier 1 — Overbuilding Synal
Fix: build fake browser UI first, not real browser.

### Barrier 2 — No live proof
Fix: every demo run writes one real lead/signal/evidence event.

### Barrier 3 — Too much language
Fix: product page must say one thing: “One announcement becomes messages, tasks, docs and proof.”

### Barrier 4 — Partner names without partner proof
Fix: label integrations as Demo/Stub/Live.

### Barrier 5 — Pricing uncertainty
Fix: price as pilot and bundles first; validate through calls.

### Barrier 6 — Visual complexity
Fix: use generated Synal image as hero, but create a simpler live UI underneath.

### Barrier 7 — Data/privacy risk
Fix: consent checkbox and data-use receipt from day one.
